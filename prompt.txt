# Build a Production-Quality 3GPP Standards RAG Chatbot

## 1. Role

Act as a senior AI/ML engineer and full-stack engineer.

Build a complete, working, production-quality Retrieval-Augmented Generation (RAG) chatbot whose primary knowledge source is official 3GPP telecommunications standards documentation.

The project is being developed as a technical hiring assignment. The most important evaluation criteria are:

1. Retrieval quality
2. Minimal to near-zero hallucinations
3. Grounded answers
4. Accurate citations
5. Correct handling of insufficient evidence
6. Evaluation methodology and measurable results
7. Clean, maintainable engineering
8. A working end-to-end implementation

Do NOT build a superficial chatbot demo. Build an actual RAG system with explicit mechanisms for preventing unsupported claims.

---

# 2. Core Objective

Build a chatbot that can answer technical questions about 3GPP standards using the indexed 3GPP documents as the source of truth.

Example question:

"What is the role of the AMF during UE registration?"

The system should:

1. Understand the query.
2. Identify relevant specification/release information if present.
3. Retrieve relevant 3GPP passages.
4. Combine semantic and lexical retrieval.
5. Rerank the retrieved passages.
6. Determine whether sufficient evidence exists.
7. Generate an answer ONLY from the retrieved evidence.
8. Attach precise citations to the answer.
9. Verify that the generated claims are actually supported by the evidence.
10. Refuse to answer when sufficient evidence is unavailable.

The system must prioritize correctness and groundedness over producing an answer.

If the system cannot establish an answer from the indexed 3GPP documentation, it should explicitly say that it cannot answer reliably.

---

# 3. Important Design Principle

Do NOT attempt to solve hallucinations merely through prompting.

Implement hallucination prevention at the system architecture level.

Use multiple safeguards:

* Metadata-aware retrieval
* Hybrid retrieval
* Reranking
* Retrieval confidence thresholds
* Evidence sufficiency checking
* Grounded generation
* Structured outputs
* Citation enforcement
* Claim-level verification
* Explicit refusal behavior
* Evaluation against unanswerable questions

The system should be designed around:

"Retrieve authoritative evidence first, then allow the LLM to synthesize only from that evidence."

# 5. Initial 3GPP Dataset

Do not attempt to download and index every 3GPP document initially.

Create a focused but representative dataset of important 5G specifications.

Prioritize specifications such as:

* TS 23.501 — System Architecture for the 5G System
* TS 23.502 — Procedures for the 5G System
* TS 24.501 — Non-Access-Stratum (NAS) protocol for 5G System (5GS)
* TS 38.331 — NR; Radio Resource Control (RRC)
* TS 29.500 — 5G System; Technical Realization of Service Based Architecture
* TS 29.501 — 5G System; Principles and Guidelines for Services
* TS 29.502 — 5G System; Session Management Services
* TS 29.503 — 5G System; Unified Data Management Services

Use official 3GPP sources wherever possible.

Do not silently substitute unofficial documents as authoritative sources.

The architecture should make it easy to add more specifications later.

# 6. Document Metadata

Preserve detailed metadata throughout the entire pipeline.

Every indexed chunk should contain metadata similar to:

```python
{
    "spec_number": "23.501",
    "title": "System Architecture for the 5G System",
    "release": "Rel-18",
    "version": "18.x.x",
    "section": "5.3.2",
    "section_title": "...",
    "page": 42,
    "source_url": "...",
    "document_id": "...",
    "chunk_id": "...",
    "text": "..."
}
```

Do not discard specification number, release, version, section or page information.

These fields are critical for:

* retrieval
* filtering
* citations
* evaluation
* debugging

# 7. Document Ingestion Pipeline

Implement a reusable ingestion pipeline:

```text
3GPP source documents
        ↓
PDF download / local ingestion
        ↓
PDF parsing
        ↓
Structure detection
        ↓
Metadata extraction
        ↓
Structure-aware chunking
        ↓
Embedding generation
        ↓
Vector index
        +
BM25 index
```

The ingestion pipeline should be executable independently from the chatbot.

For example:

```bash
python -m ingestion.run
```

or an equivalent command.

Do not require the developer to manually edit Python files to ingest documents.

# 8. PDF Parsing

3GPP documents are structured technical documents.

Do NOT simply split extracted text into arbitrary fixed-size chunks.

Preserve:

* document title
* specification number
* release
* version
* chapter
* section
* subsection
* paragraph
* tables where reasonably possible
* page number

If the PDF parser can detect headings, use those headings to reconstruct document hierarchy.

Example:

```text
TS 23.501
  Chapter 5
    5.3 Registration Management
      5.3.1 ...
      5.3.2 ...
```

The chunk metadata must retain this hierarchy.

---

# 9. Chunking Strategy

Implement structure-aware chunking.

Preferred hierarchy:

```text
Document
  ↓
Section
  ↓
Subsection
  ↓
Paragraph groups
```

A section should remain intact when reasonably small.

If a section is too large, split it into smaller chunks based on paragraph boundaries rather than blindly cutting text in the middle of sentences.

Use a configurable token/character limit.

Each chunk should include enough surrounding context to remain meaningful.

For example:

```text
Specification: TS 23.501
Release: Rel-18
Section: 5.15.6
Section title: AMF Services

[chunk text]
```

Consider adding the section heading and specification information into the indexed text as contextual prefixes.

---

# 10. Embeddings

Create embeddings for every chunk.

The embedding model must be configurable.

Do not hard-code the embedding model throughout the application.

For example:

```env
EMBEDDING_MODEL=...
```

Use a strong general-purpose embedding model suitable for technical text.

The architecture should make changing the embedding model straightforward.

# 11. Vector Database

Use FAISS or Qdrant.

For a simple initial implementation, FAISS is acceptable.

Store:

* vector
* chunk text
* chunk ID
* specification metadata
* release
* version
* section
* page
* source URL

The retrieval layer should return both the text and complete metadata.

---

# 12. BM25 Retrieval

Implement lexical retrieval in addition to vector search.

This is especially important because 3GPP contains highly specific identifiers such as:

* AMF
* SMF
* UPF
* UE
* N1
* N2
* N3
* T3510
* PDU Session
* Registration Request
* NAS
* RRC

Exact keyword matching can outperform semantic retrieval for such identifiers.

Implement:

```text
Query
 ├── Vector retrieval
 └── BM25 retrieval
```

Retrieve a configurable number of candidates from each.

---

# 13. Hybrid Retrieval

Implement a hybrid retrieval strategy.

Example:

```text
Vector Search → top 20
BM25          → top 20
                    ↓
              merge / deduplicate
                    ↓
              candidate pool
```

Use a sensible score-combination strategy.

Keep the implementation configurable.

Do not simply concatenate the two result sets without considering their ranking.

---

# 14. Metadata-Aware Retrieval

If the user specifies a specification, use it.

Example:

User:

"According to TS 24.501, what is T3510?"

The system should identify:

```text
spec_number = 24.501
```

and restrict retrieval to that specification when possible.

Similarly, if a release is explicitly specified:

"According to Rel-18..."

filter to the requested release.

Implement automatic extraction of specification identifiers using deterministic parsing/regex where appropriate.

For example, recognize:

* TS 23.501
* TS23.501
* 23.501

Do not rely entirely on an LLM for this.

---

# 15. Query Understanding

Create a lightweight query-analysis stage.

Extract information such as:

```json
{
    "specification": "23.501",
    "release": "Rel-18",
    "keywords": [
        "AMF",
        "registration"
    ],
    "query": "What is the role of the AMF during registration?"
}
```

The specification and release fields may be null if not present.

Do not over-engineer this stage.

Use deterministic extraction for obvious entities and optionally an LLM for more complex query interpretation.

---

# 16. Reranking

After hybrid retrieval, rerank the candidate chunks.

Example:

```text
Hybrid retrieval
       ↓
40 candidates
       ↓
Reranker
       ↓
Top 5–10 evidence chunks
```

Use a cross-encoder or another appropriate reranking model.

Make the number of retrieved and final chunks configurable.

---

# 17. Evidence Sufficiency Check

This is a critical component.

Before generating the final answer, determine whether the retrieved evidence is sufficient to answer the question.

Create an evidence evaluation step.

Input:

```text
Question:
...

Retrieved evidence:
...
```

Output:

```json
{
    "sufficient": true,
    "confidence": 0.94,
    "reason": "The retrieved sections explicitly describe the requested procedure."
}
```

If evidence is insufficient:

```json
{
    "sufficient": false,
    "confidence": 0.31
}
```

Do NOT generate a speculative answer.

Instead return a clear refusal such as:

"I could not find sufficient evidence in the indexed 3GPP specifications to answer this reliably."

Do not invent information.

---

# 18. Grounded Generation

The generation model must receive:

1. User question
2. Retrieved evidence
3. Metadata
4. Strict grounding instructions

Use a prompt similar in principle to:

```text
You are a 3GPP standards question-answering assistant.

Answer ONLY using the supplied evidence.

Rules:

1. Do not use outside knowledge.
2. Do not invent facts.
3. Do not infer unsupported technical behavior.
4. Every factual claim must be supported by supplied evidence.
5. Cite the relevant specification and section.
6. Never fabricate page numbers or specification numbers.
7. If the evidence is insufficient, explicitly say so.
8. If sources conflict, explain the conflict.
9. Prefer the user-requested release when specified.
10. Do not claim certainty when the evidence does not support certainty.
```

The exact wording can be improved during implementation.

---

# 19. Structured Answer Output

Do not allow the LLM to return arbitrary text internally.

Use structured output such as:

```json
{
    "answer": "...",
    "grounded": true,
    "confidence": 0.94,
    "claims": [
        {
            "text": "...",
            "source_chunk_ids": [
                "..."
            ]
        }
    ],
    "sources": [
        {
            "spec_number": "23.501",
            "release": "Rel-18",
            "version": "...",
            "section": "5.3.2",
            "page": 42,
            "source_url": "..."
        }
    ]
}
```

The frontend can then render this cleanly.

# 20. Citation Enforcement

Every substantive answer must contain citations.

Citations should include as much of the following as the source metadata supports:

* Specification number
* Release
* Version
* Section
* Section title
* Page
* Source URL

Example:

```text
TS 23.501
Rel-18
Section 5.3.2
Page 42
```

Do not fabricate citation metadata.

If a page number cannot reliably be determined, omit it rather than inventing one.

---

# 21. Claim-Level Verification

Implement a post-generation verification stage.

Pipeline:

```text
Retrieved Evidence
       +
Generated Answer
       ↓
Claim Extraction
       ↓
Claim Verification
       ↓
Supported / Unsupported
```

For each factual claim, determine whether it is supported by the retrieved evidence.

Example:

```json
{
    "claim": "The AMF performs registration management.",
    "supported": true,
    "evidence_chunk": "chunk_123"
}
```

If an important claim is unsupported:

* either regenerate using stricter constraints
* or reject the answer and return an uncertainty/refusal response

Never silently present unsupported claims as facts.

---

# 22. Answer Regeneration

If claim verification fails, allow one controlled retry.

Example:

```text
Generate
   ↓
Verify
   ↓
Unsupported claim?
   ↓
Retry with stricter grounding
   ↓
Verify again
   ↓
Still unsupported?
   ↓
Refuse
```

Do not create infinite retry loops.

Maximum retry count should be configurable and default to 1.

---

# 23. Handling Unanswerable Questions

This is mandatory.

Create questions where the answer is NOT available in the indexed documents.

Examples:

* Questions unrelated to telecom
* Questions about unsupported specifications
* Questions asking for facts absent from the documents
* Questions containing fabricated standards
* Questions requiring information from a release that isn't indexed

The correct behavior is:

```text
I could not find sufficient evidence in the indexed 3GPP
specifications to answer this reliably.
```

This is preferable to hallucinating.

---

# 24. Handling Conflicting Releases

The system must not mix information from different releases without making that clear.

If Rel-17 and Rel-18 contain different information:

```text
Rel-17:
...

Rel-18:
...
```

The answer should explicitly identify the difference.

If the user specifies a release, prioritize that release.

# 47. Most Important Instruction

Do not optimize for "the LLM gives an answer."

Optimize for:

```text
Can the system prove that its answer came from
the correct 3GPP evidence?
```

When evidence is available:

```text
Retrieve → Verify → Answer → Cite
```

When evidence is unavailable:

```text
Retrieve → Fail Evidence Check → Refuse
```

The second behavior is just as important as the first.

Build the project accordingly.
